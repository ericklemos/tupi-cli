# Optimizer Journal

## 2026-11-13 - Quadratic Graph Resolution in GraphBuilder::build
**Bottleneck:** Building the code graph for `tupi-cli` (~90 files, 2,280 nodes, 6,335 edges) took **2.135s** in debug mode because `GraphBuilder::build` scanned all `graph.graph.node_indices()` inside the per-call-site loop ($O(C \cdot N)$), linearly searched all containers per member ($O(M \cdot K)$), scanned all nodes per file for callers ($O(F \cdot N)$), cloned `FileScope` on every call site, and parsed/hashed each file multiple times.
**Learning:** Whenever `GraphCache` invalidates on file edits, `GraphBuilder::build` rebuilds the whole graph from scratch, so $O(C \cdot N)$ call resolution dominates latency even on medium-sized repos.
**Optimization:** Indexed containers by name, callers by relative path, and definitions by `(Language, name)` once in $O(N)$ using `Cow<'_, [NodeIndex]>` borrows, borrowed `&FileScope` once per file, deferred `collect_bindings` until a non-`self` receiver call needs it, and parsed/hashed each file once via `AstChunker::snippets_from_tree` + `ParseCache::parse_with_digest`. Runtime dropped to **803ms** (2.66x faster).

## 2026-11-14 - `BacktrackGraph` eviction is the real cost of a broad `search`, and "one pass" eviction is slower
**Bottleneck:** `SearchTool::search` records a `Frontier` visit for **every cut result** (`for &(index, _) in ranked.iter().skip(max_results)`) via `BacktrackGraph::record_visit`. Each call takes the `Mutex`, allocates a `NodeId` (2 `String`s) plus `via.to_string()`, and ends with `State::evict_if_needed`. Once `nodes` hits `DEFAULT_MAX_NODES` (**1024**), that function looped `min_by_key(last_touched)` over the whole map — $O(n)$ **per insert**, i.e. $O(k \cdot n)$ for $k$ cut results.
**Learning:**
- Measured at 16,000 candidate snippets (debug): search took **719ms** with capacity 1024 vs **455ms** with capacity 1M → eviction alone is **264ms (37%)**. The `ranked.sort_by` comparator that calls `visit_level` twice per comparison is only **4-10ms** (<1.5%) — the tempting "hoist the lock out of the comparator" fix is a rounding error by comparison.
- **The theoretically better data structure lost.** Replacing the per-removal `min_by_key` scan with a "single pass" bulk eviction (`collect last_touched` + `select_nth_unstable` + `retain`) made the same workload go **719ms → 1,253ms (+74%)**. Reason: eviction is invoked for *one* node at a time, so a single `HashMap::iter().min_by_key()` pass (with exactly one `NodeId::clone`) beats three sequential passes plus a fresh `Vec<u64>` allocation. Bulk eviction only pays off when many nodes are removed per call.
- `last_touched` comes from a monotonic clock and is therefore unique per node — which is what makes a `retain(>= cutoff)` formulation exactly equivalent to removing the minimum repeatedly.
**Optimization:** **None landed.** The correct fix is to remove the per-item eviction entirely: batch the cut-result visits (`record_visits(&[VisitRequest])` — one lock, one eviction pass, $O(k + n)$), keeping `record_visit` as a one-element batch. That needs a new small type in `crates/tupi-tools/src/support/backtrack.rs`, which was not reachable with this session's editing tools (see results file). Both probe changes were reverted; the tree is byte-identical and `cargo test -p tupi-tools --lib` is green (376 tests).
